# 上下文压缩：讨论与调查记录

> 记录 2026-10-20 对上下文压缩的讨论、基于基准测试 trace 的调查数据，以及由此得出的结论和待办事项。压缩机制本身的设计见 [上下文管理](context-management.md)。

---

## 1. 现状（同步压缩，已实现）

- **触发**：每次调用模型之前，若上下文 token 数超过 `maxContextTokens × warningWatermark`（默认 128k × 0.8 = 102.4k），就先压缩。检查放在调用之前，是因为 GitHub App 会话接着已有对话继续时会追加一条消息（新提交的 diff 或作者回复），它本身就可能让上下文越过阈值。
- **分区**：冻结区（system 和初始任务，永不修改）→ 记忆槽（每次压缩时替换）→ 被压缩的历史 → 保留原样的最近轮次（预算为 102.4k × 0.5 减去冻结区）。
- **记忆槽**：确定性轨迹（工具名和参数，以及 `[event]` 事件行，不经过 LLM）加 LLM 摘要（旧摘要与被压缩的工具结果合并重写）。只有被压缩的轮次进入轨迹，保留原样的轮次不会重复记录。
- **缓存**：冻结区的前缀一直命中；记忆槽之后的内容每压缩一次重建一次。
- **token 计数**：用 js-tiktoken（OpenAI 的 `cl100k` 分词器）估算整段消息。下文的调查表明，这个估算对 DeepSeek 明显偏低。

## 2. 讨论记录

### 2.1 异步压缩（规划中，未实现）

- **触发与替换都在两轮之间**：到达 `softWatermark`（0.6）时，在一轮结束的位置拍快照，后台压缩；Agent 继续执行。后台完成后，在下一次调用模型之前换入，因此 tool_call 与 tool 结果始终成对。
- **到达同步阈值（0.8）**：后台压缩还在进行就等待它完成；换入后仍超过阈值，再做一次同步压缩。后台压缩失败或从未启动，就直接同步压缩。
- **快照前的内容怎么处理**：
  - **方案 A**：全部压缩，只保留快照之后新增的轮次。简单，压缩幅度最大。但如果后台很快完成，快照之后可能只有 0～1 轮，模型刚读过的文件只剩轨迹里的一行，大概率要重读。
  - **方案 B（选定）**：全部压缩，但设一个下限。换入后原样保留的内容至少 N 个 token；快照之后新增的不够时，从快照之前补上最近的几轮。补回的轮次保持原样，不提取进轨迹。
- **收益**：压缩的 LLM 调用和 Agent 的后续轮次并行，延迟被藏起来，花费不变，缓存命中情况和同步压缩相同。

### 2.2 会话复用带来的问题

- **冻结区里的 diff 会过时**：会话里的初始任务永远是第一次审查时的 diff。目前靠后续消息里的"之前读到的内容可能已过时"提醒模型。
- **决定**：到了合适的时机就**新开会话**，冻结区随之重建（以当前 head 的 diff 为准，以 GitHub 上的历史发现为种子），而不是在旧会话里修改冻结区。force-push 后已经会这样做；其他时机（推送次数、会话真实 token 数、冻结区 diff 与 head 的差异程度）等有了数据再定。
- **会话只增不减**：旧轨迹在每次压缩时原样保留，推送很多次的 PR 轨迹会一直变长。可能需要给轨迹设上限，超出后对最早的部分再做一次摘要。

### 2.3 成本与质量

- 摘要调用会重新发送全部被压缩的工具结果，是一次未命中缓存的大请求，这是压缩的主要开销。
- DeepSeek 的缓存命中价约为未命中的 1/50，长上下文本身并不贵。压缩的主要价值是守住上下文窗口和注意力质量，而不是省钱。
- 要回答"压缩会不会导致重读或重复报告"，必须用数据说话，于是有了下面的调查。

## 3. 调查

### 3.1 数据与方法

- **数据**：本地 42 次基准测试审查（aacr30-flash 29 次、sanity10-seed7 9 次，其余 4 次），共 195 个文件组、2135 轮。每条 trace 按轮记录 DeepSeek 计费的 `promptTokens`、工具调用和工具结果。
- **识别压缩**：同一文件组内，若某一轮的 prompt token 数降到上一轮的 80% 以下，视为中间发生了压缩。
- **估算校准**：
  - 首轮请求正好是 [system, 初始任务]，直接比较估算值与计费值；
  - 之后每轮，比较"真实 prompt 的增长量"与"上一轮新增内容（回复、工具调用、工具结果）的估算值"。

### 3.2 结果

**压缩从未触发。** 195 个文件组里压缩触发 0 次。各组上下文峰值（计费 prompt token）：

| p50 | p90 | 最大 | 超过 102.4k | 超过 61.4k（0.6） |
| :-- | :-- | :--- | :---------- | :---------------- |
| 22k | 52k | 153k | 1 组        | 10 组（约 5%）    |

唯一超过阈值的是 ClickHouse 的一个文件组：上下文从 102k 涨到 153k，始终未触发压缩，最后因用满轮数停止。DeepSeek flash 接受了 153k 的请求，说明它实际的上下文窗口大于配置中的 128k；根据 models.dev，实际为 1M（见第 5 节）。

**原因：估算比计费值低约 1.7 倍。**

| 校准方式                | 计费 / 估算                                                          |
| :---------------------- | :------------------------------------------------------------------- |
| 每轮新增内容（2135 轮） | 1.70                                                                 |
| 首轮请求（194 次）      | 1.71，另有每次约 1.4k 的固定开销（工具定义和消息格式，估算完全没算） |

两种口径一致，说明这是分词器之间的系统性差异：同样的代码文本，DeepSeek 切出的 token 约多 70%。平均每个 DeepSeek token 对应 2.35 个字符，`cl100k` 约为 4 个。结果是，"102.4k 阈值"实际要到约 174k 计费 token 才会触发。

**单轮估算误差（每轮增长大于 200 token 的 2085 轮）：**

| 估算方法       | 误差 p10 | p50  | p90  | 绝对误差 p90 |
| :------------- | :------- | :--- | :--- | :----------- |
| 字符数 ÷ 2.35  | −72%     | +8%  | +57% | 77%          |
| tiktoken × 1.7 | −70%     | +14% | +50% | 70%          |

两者单轮误差都很大且相近，tiktoken 并不比按字符估算更准。

**重读：** 1659 次 `read_file` 中，417 次（25%）重读了同一文件，全部发生在没有压缩的情况下，多半是读同一文件的不同行段。因为没有任何一次压缩，"压缩导致重读"目前无法评估。

## 4. 结论

1. **压缩代码在实际运行中基本没有被执行过**。在测量修好之前，异步压缩的收益接近于零，也拿不到压缩质量的数据。
2. **token 测量应以 API 返回值为准**。LLM API 每次都会返回刚发出请求的真实 `prompt_tokens`，但它是事后数据，而压缩要在下一次请求发出之前决定。下一次请求比上一次多出：
   - 上一次的回复：`completion_tokens` 包含不会回传的 reasoning token，直接用会偏大；
   - 这一轮的工具结果；
   - 会话中追加的后续消息。

   因此判断依据应为：上一次的真实 `prompt_tokens` 加上新追加内容的估算。估算只覆盖新增的一小段，误差影响很小。判断时要留出余量，单次工具输出上限为 40k 字符，约 17k token。

3. **js-tiktoken 可以移除**。新增内容的估算，以及审查开始前（还没有任何 API 返回值时）的文件过大过滤和分组预算，都可以改用"字符数 ÷ 2.35"，或者偏保守地用 ÷ 2。tiktoken 的精度并不更高。
4. **会话场景才是压缩真正起作用的地方**。单次审查只有约 5% 的文件组越过 0.6；而推送多次、讨论多轮的 PR，会话会持续增长。目前只有一个会话样本（PR #2，28 条消息），新开会话的标准要等有数据再定。

## 5. 业界做法参考

查看了两个开源 agent harness 的源码（2026-10-20），它们都不用分词器，而是以**最近一次响应里 API 报告的 usage** 为锚点，再加上锚点之后新增消息的字符估算：

|          | opencode（anomalyco/opencode）                                                                                                 | pi（earendil-works/pi）                                                           |
| :------- | :----------------------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------- |
| 实测部分 | 最近一条 assistant 消息的 `input + cache.read + cache.write + output + reasoning`；只信任同一 provider、未报错、计数非零的消息 | 最近一次 assistant 的 `totalTokens`，或 `input + output + cacheRead + cacheWrite` |
| 估算部分 | 锚点之后的消息（含锚点那一轮本地执行的工具结果）按字符数 ÷ 4；还没有响应时估算整个请求，包括 system 和工具定义                 | 锚点之后的消息按字符数 ÷ 4                                                        |
| 触发上限 | 窗口 − max(10%, 16k)，窗口来自 models.dev；窗口未知时不设上限                                                                  | 窗口 − `reserveTokens`（16384）；压缩时保留最近约 20k token                       |
| 过期计数 | —                                                                                                                              | 在某次编辑或压缩之前记录的 usage 不再使用，改为重新估算                           |
| 兜底     | provider 返回"上下文过长"时，把目标依次缩到估算值的 0.7 / 0.5 / 0.35 后重新压缩                                                | —                                                                                 |

对本项目的启示：

- 第 4 节的测量方案与两者一致。它们按 ÷ 4 估算，而 DeepSeek 处理代码的实测是 ÷ 2.35，所以新增部分应使用实测系数。
- 压缩后、下一次响应前，上一次的 usage 已经作废，要对整段消息重新估算。会话恢复时也一样，会话文件目前不保存每条消息的 usage。
- 可以加上 opencode 那种"被拒绝后按比例缩小再压缩"的兜底。
- **窗口应来自模型目录**：models.dev 登记的 `deepseek-flash`、`deepseek-v4-flash`、`deepseek-v4-pro` 上下文窗口均为 1M，输出上限 393k，这也解释了 ClickHouse 那次 153k 的请求为何没有出错。配置中的 128k 不是模型限制。因此在 DeepSeek 上，压缩的作用从"防止溢出"变成了"有意控制上下文长度，以保证注意力质量和成本"，`maxContextTokens` 的取值需要用基准测试数据来定。

## 6. 待办（按顺序）

1. **修正 token 测量**：压缩判断改为"上一次计费的 `prompt_tokens` + 新增内容的字符估算"；预检和分组改用字符估算；移除 js-tiktoken；trace 中记录每次压缩（压缩前后的 token 数、摘要调用的花费）。
2. **重跑一小批基准测试**（如 sanity10），统计压缩的真实触发频率、压缩后的重读率与重复报告率。
3. **依据数据决定**：异步压缩（方案 B）是否值得实现、下限 N 取多少；会话新开的标准；轨迹是否需要上限。
4. **重新定义 `maxContextTokens`**：DeepSeek 的窗口为 1M（models.dev），128k 只是有意设定的上下文预算。用基准测试数据确定这个预算，并从模型目录读取真实窗口，作为不可越过的硬上限。
